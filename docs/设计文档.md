# 刀剑乱舞ぱずぎり MAA 设计文档

状态：设计稿，待评审  
最近更新：2026-10-14

## 项目目标

构建一个基于 MaaFramework 的《刀剑乱舞ぱずぎり》自动化项目，优先通过 MuMu 模拟器运行，只适配游戏官方日文界面。项目使用 Maa 标准项目结构，并将游戏流程、视觉识别、连线棋盘建模和策略计算分层，便于先搭建框架，再用实际画面验证实现选择。

## 已确认的范围

- 使用 MaaFramework 与 Project Interface V2。
- 首选 MuMu 模拟器及 ADB 控制。
- 只适配官方日文界面。
- 运行界面采用 MFAAvalonia。首版通过配置设置窗口初始分辨率和 Dashboard 卡片布局。
- 棋盘是连线形消除玩法，棋盘及棋子位置不固定，棋子可能有不同尺寸，并存在可点击使用的炸弹等道具。
- YOLO 作为棋子和道具定位的主要候选方案；最终类别、模型和推理接入方式须由实际截图验证。
- 后续可能为 MFAAvalonia 增加侧边栏仓库入口或其他游戏专属功能。

## 项目框架与开发工具

### create-maa-project

使用 [create-maa-project](https://github.com/Windsland52/create-maa-project) 作为本项目唯一的框架生成与维护工具。为棋盘重建、识别后处理和策略计算预留 Python 自定义逻辑，创建时选择 `agent` 项目类型，并启用 ADB 控制目标。开发工具和 GitHub 工作流按实际维护需要选择。

该工具负责生成及维护项目结构、Project Interface、资源目录和开发工具配置；业务 Pipeline、识别模型、策略代码仍由本项目实现。它也提供 MaaFramework 与 MFAAvalonia 运行时资产同步能力。生成后使用 `--doctor` 检查项目状态；构建、打包和发布由生成项目提供的开发工具及工作流承担。

### Everything-Maa

将 [Everything-Maa](https://github.com/KhazixW2/Everything-Maa) 作为 Codex 开发辅助技能，参考 Maa 项目、Pipeline、Agent 和调试工作流。它与 create-maa-project 的创建技能可以配合使用，但项目文件的生成和维护仍交由 create-maa-project，避免两套工具重复管理同一批文件。

### MaaPracticeBoilerplate

[MaaPracticeBoilerplate](https://github.com/MaaXYZ/MaaPracticeBoilerplate) 作为 Maa 标准结构、Project Interface V2 和 MFAAvalonia 集成方式的参考资料，不再作为第二套项目生成器。这样保留标准 Maa 约定，同时由 create-maa-project 统一维护项目状态和受管文件。

## M9A 与界面扩展参考

[M9A](https://github.com/MAA1999/M9A) 的公开资源接口包含 GitHub 仓库地址、Agent 配置和多个资源包；其说明和发布包也展示了 MFAAvalonia、MXU 等通用客户端的使用方式。它适合作为大型 Maa 资源项目的组织参考。已确认 M9A 没有侧边栏仓库入口，因此不能把它当作该界面功能的现成范例。

M9A 的 `interface.json` 中有 GitHub 仓库元数据。我们也应在本项目接口中维护仓库地址，供支持该字段的客户端功能使用；但仓库元数据本身不会提供侧边栏入口。若后续决定加入该入口，需要自行修改 MFAAvalonia，并把个性化客户端构建接入项目发布流程。

## MFAAvalonia 配置与定制路线

- 在 `config/config.template.json` 中设置 `UI.MainWindow.Width` 与 `UI.MainWindow.Height`，作为新安装的初始窗口尺寸。该模板只在没有现存用户配置时生效。
- 在资源包中提供 `mfa_layout.json`，设置 Dashboard 卡片的行列、间距和卡片位置。它可以调整任务卡片布局，但不负责添加侧边栏导航。
- PI 中继续维护本项目 GitHub 仓库地址，作为项目元数据和客户端更新配置使用；它不替代侧边栏功能。
- 若后续决定实现侧边栏仓库入口，则基于 MFAAvalonia 增加入口及对应页面或外链交互，并维护个性化分支。资源项目仍按 Maa 标准 PI V2 接入；客户端源代码和定制补丁单独维护，发布工作流固定使用经过验证的版本。
- 初期先用通用 MFAAvalonia 验证资源和任务流程，确认侧边栏入口的交互和呈现需求后再接入个性化客户端，减少 GUI 定制对自动化开发的阻塞。

## 运行架构

### 游戏流程

Pipeline 负责启动游戏、页面导航、进入关卡、等待动画稳定和确认操作结果。Project Interface V2 声明任务、选项和控制器，使 MFAAvalonia 能加载资源并执行任务。识别与策略需要复杂逻辑时，由 Pipeline 调用 Python Agent。

### 棋盘表示与视觉识别

不能将棋盘预设为固定行列或固定格子坐标。每帧棋盘状态至少需要表达：

- 棋盘区域和当前布局。
- 每个棋子或道具的检测框、中心点、类别、尺寸或占位范围及置信度。
- 棋子之间可连线的节点与边，以及当前连线规则所需的状态。
- 炸弹等可点击道具的位置、可用状态和对应点击坐标。
- 当前画面是否处于稳定状态，是否被动画、特效或遮挡影响。

建议以 YOLO 目标检测定位可变位置的棋子和道具，再由 Agent 根据检测框、棋子中心点和画面几何关系重建棋盘图结构。尺寸不同的棋子需要保留实际边界框或占位信息，不能只按一个中心点塞入固定格子。炸弹等道具应作为独立类别和交互目标处理。

棋子外观类别较多时，可先让 YOLO 负责定位对象与粗类别，再对检测框裁剪图做细分类；具体类别应按消除规则决定，例如区分可互相匹配的棋子类型、尺寸和特殊状态。棋盘图构建与消除策略由 Agent 负责，Pipeline 负责调度和执行返回的动作。

MaaFramework 的 `NeuralNetworkDetect` 支持 YOLOv8、YOLOv11 导出的 ONNX 模型，适合寻找任意位置的目标，但官方说明其训练数据、模型复杂度和推理开销通常高于固定区域分类。它可以作为模型接入候选；如果框架检测结果不便表达棋盘图和策略需要的状态，则由 Python Agent 完成模型推理及后处理。两种接入方式共用同一份棋盘状态定义，便于比较和替换。

训练前先采集官方日文界面的真实截图，覆盖不同棋盘布局、棋子类型与尺寸、炸弹可用或已使用状态、分辨率、动画和特效。标注集应覆盖棋子和道具的边界框及类别。评估不只看目标检测精度，还要检查棋盘节点和连线重建准确率、合法操作比例，以及操作后状态确认成功率。

### 棋盘重建与策略

Agent 将视觉检测结果转为图结构：节点表示可操作棋子或位置，边表示规则允许的连线关系；节点数据保存类别、大小、占位和道具状态。策略模块只接收已校验的图状态，计算符合游戏规则的连线或道具操作，并输出屏幕坐标和动作序列。

游戏规则、棋子大小如何影响连线、炸弹的触发方式和优先级需通过实际游玩画面或说明确认。在这些规则验证前，不固定具体寻路算法、类别表或炸弹策略。

## 控制与识别

- 通过 ADB 连接 MuMu，验证设备发现、截图、点击和滑动。
- 页面导航先用模板匹配、颜色识别和日文 OCR；只制作官方日文界面的识别资源。
- 每次棋盘动作前获取稳定截图；动作后等待动画结束，再重新识别并校验状态变化。
- 识别结果低置信度、图结构无法校验、页面状态未知或动作结果不符预期时，停止任务并保存日志和截图。

## 实施阶段

1. 评审本设计稿，确认脚手架、GUI 路线和 YOLO/Agent 识别边界。
2. 使用 create-maa-project 创建 Agent 项目，选择 ADB 控制，并检查生成的 PI V2、目录和发布工作流。
3. 通过通用 MFAAvalonia 验证 MuMu 连接、初始窗口尺寸和 Dashboard 默认布局。
4. 采集官方日文界面截图，记录页面流程、棋盘结构、棋子大小、消除规则和炸弹交互。
5. 建立棋子与道具数据集，比较 YOLO 定位和可行的传统图像处理方案，确定模型及 Agent 接入方式。
6. 实现动态棋盘图重建、规则校验和策略计算，再通过 Pipeline 执行动作并确认结果。
7. 如需独立侧边栏仓库入口，定制 MFAAvalonia 并将客户端构建纳入发布流程。
8. 验证资源打包、客户端集成和最终发布产物。

## 首版验收目标

- create-maa-project 生成的 Maa 标准 Agent 项目可被 MFAAvalonia 正确加载。
- 可在 MuMu 上稳定连接、截图并执行基本触控操作。
- 资源限定为官方日文界面，窗口初始尺寸和 Dashboard 默认卡片布局符合设定。
- 识别结果能表达可变棋盘、不同尺寸棋子和可点击道具，并能重建合法连线关系。
- 策略只对校验通过的棋盘状态产生合法操作；低置信度或执行异常时安全停止。
- 发布产物包含 MaaFramework 运行组件、资源、Python Agent 和选定的 MFAAvalonia 客户端。
